## 0. 结论

评审基线的代码本身是健康的：111 个测试文件 / 996 个用例全绿，`tsc --noEmit` 干净，CI 闸门齐全，`lib/` 九域边界清晰。

缺口在代码之外，形态都一样——**流程写成了文档，没有写成可执行的东西**：

1. **约束层没有执行力。** `CLAUDE.md` 与 `AGENTS.md` 写满了关键不变量，但没有任何机制阻止它们与代码脱节，而它们已经脱节。
2. **AI 功能没有验证层。** coach 是付费功能，行为由十余条散文规则定义；测试只验证「prompt 里有这句话」，从未验证「模型照做了」。
3. **harness 不是仓库资产。** `.claude/` 被整个 gitignore，可复用的工作流全靠人记。

本次把这三层补上。补上的验证层在第一次真实运行时就抓到了一个 **P0 缺陷**（§3.1）：在推理模型下，付费 coach 对分析类问题返回空回复。修复后的代码默认值对所有 DeepSeek 模型名都正确，部署即生效，不依赖生产环境变量。

## 2. AI 导师人设的合规问题

### 问题

五位导师此前使用真实职业棋手的身份（其中四位在世）：四语言真名、国旗、生平，以及让模型以第一人称扮演该人物的系统指令，部分还带有贬低学生的语气设定。这些人设位于 Stripe 订阅之后。`LEGAL_COMPLIANCE.md` 覆盖了 GDPR、DMCCA、特商法等，**完全没有涉及人格权**。

付费服务中商业性使用真人身份，在 go-daily 的所有主要市场都构成独立法律风险（中国《民法典》人格权编、日本パブリシティ権、韩国《不正竞争防止法》第 2 条第 1 项타目、美国各州 right of publicity）。判断标准是可识别性，不是是否写出名字。

### 处理

- **人设虚构化**：改为五个基于棋风原型的原创角色——疾风、深流、止水（新默认）、磐石、明镜。新 id、主题符号 `emblem` 取代 `flag`，系统指令只描述讲解语气，不让模型扮演身份；删除贬低学生的语气设定。
- **兼容**：`personaId` 不落库，无需数据迁移。部署时仍开着旧页面的用户会发送旧 id，`CoachRequestSchema` 将无法识别的 id 降级为默认导师，而不是让付费功能返回 400。
- **可见披露**：导师页（移动端与桌面端两套布局）和导师选择面板显示虚构角色声明。
- **机械防护**：`tests/lib/coach/personas.test.ts` 检查人设相关文件是否出现真实棋手姓名（四种文字，含已下线的全部译名和其他知名棋手）、`emblem` 是否为国旗、系统指令是否含身份声明。负向测试确认塞回真名或国旗会报红。judge 校准集另含一条「贬低学生」样例，确认人设语气评分器会拒绝旧式语气。
- **历史对局叙事**：首页与 about 页讲述 2016 年人机大战第四局。这是对公开历史事件的事实性介绍，予以保留；因 about 页将品牌与该局故事绑定，补了不关联声明。
- **法律文档**：四语言 `LEGAL_COMPLIANCE.md` 新增第 4 节「人格权与 AI 人设」（风险、处理、红线），原第 4 节顺延为第 5 节。
- **上下文**：人设虚构化写入 `CLAUDE.md` / `AGENTS.md` 与 `CRITICAL_INVARIANTS`。

`CHANGELOG.md` 中 `[1.0.0] - 2026-04-01` 的历史条目仍记录了当时上线的人设名单。那是对已发布内容的历史记录，没有改写。

## 3. eval 真实运行发现的问题

### 3.1 P0：推理模型下 coach 返回空回复

首次 live run **7/16 失败，全部是空回复，且全部是分析类问题**（「我该下哪里」「为什么下错」「急所在哪」）；打招呼、拒答越界这类短回复全部通过。

诊断（直接调用生产 provider，非推断）：

| 调用                                             | finish_reason | 推理 token | 可见内容 |
| ------------------------------------------------ | ------------- | ---------- | -------- |
| `max_tokens=400`                                 | `length`      | 400 / 400  | 0 字符   |
| 生产 provider（流式，`/api/coach` 同一代码路径） | —             | 输出 400   | 0 字符   |
| `max_tokens=2000`                                | `stop`        | 637        | 771 字符 |

根因：`max_tokens` 硬编码为 `400`，而 `deepseek-v4-flash` 默认开启 thinking，隐藏推理计入同一预算，可见内容为零。

单靠加预算不够。thinking 开启时，「为什么下错」在 2000 预算下推理 1509 / 1659 / 2000+ / 2000+ token，约 10 秒，约一半仍被截断。提示词已经给出正解、错招分支和解析，隐藏推理主要在重复推导已知答案。另据 [DeepSeek 官方文档](https://api-docs.deepseek.com/guides/thinking_mode/)，thinking 模式不支持 `temperature`——coach 的 `0.6` 此前一直被静默忽略。

对 api.deepseek.com 实测模型名（`/models` 只列出 `deepseek-flash` 与 `deepseek-v4-pro`，但别名均可用）：

| `COACH_MODEL`       | 实际解析为       | thinking 默认 | 接受 `disabled` |
| ------------------- | ---------------- | ------------- | --------------- |
| `deepseek-chat`     | `deepseek-flash` | 关            | ✅              |
| `deepseek-v4-flash` | `deepseek-flash` | **开**        | ✅              |
| `deepseek-reasoner` | `deepseek-flash` | **开**        | ✅              |
| `deepseek-flash`    | `deepseek-flash` | **开**        | ✅              |

`deepseek-chat` 并未退役（第三方文章的说法不成立）。但同一个模型只因名称不同就在「2 秒回答」和「空回复」之间切换，这正是该由代码默认值兜住的配置陷阱。

修复：

- `max_tokens` 改为 `COACH_MAX_TOKENS`（默认 2000，校验范围 256–16000）。
- 新增 `COACH_THINKING`。**未设置时按端点主机决定**：`api.deepseek.com` 发送 `disabled`，其他主机什么都不发送（`resolveThinking`）。按主机而非模型名判断，备用端点若是另一家服务商也不会收到未知参数；备用端点另有 `COACH_FALLBACK_THINKING`。
- 结果：无论生产 `COACH_MODEL` 填哪个 DeepSeek 名称，部署后默认行为都正确。

| 配置                                 | 全量结果  | 延迟           | 输出 token  |
| ------------------------------------ | --------- | -------------- | ----------- |
| thinking 开启，预算 400（修复前）    | 9/16      | —              | 400（截断） |
| thinking 开启，预算 2000             | 14/16     | 1.5–10.6 秒    | 最高 2000+  |
| **默认配置（修复后，未设任何变量）** | **16/16** | **0.8–2.7 秒** | **29–270**  |

四语言 `OPERATIONS_QA.md` 原写「`COACH_MODEL` 可切换为 `deepseek-reasoner`」却没提 token 预算——这正是导致空回复的操作。已改写并记录上表。

### 3.2 人设简介覆盖行为规则

`greeting-ko`（学生只说「안녕하세요」）在 thinking 开启时 4 次运行失败 3 次：「明镜」主动宣布学生的落子正确。

根因：系统提示词中人设简介排在行为规则之前，没有任何一句话说明两者冲突时谁优先。

修复：在简介之后加优先级声明（简介只决定语气，以下规则全部优先），并把问候规则明确为「在学生询问之前不要评价落子是否正确」。结构测试确保每位导师的简介与其保护的规则之间都有这句声明。

使用校准后的 judge（§3.3）验证：修复后 `greeting-ko` 与 `greeting-zh` 各 5/5；去掉修复的消融对照为 4/5。样本量 n=5，方向一致但不足以视为定论。

### 3.3 judge 评分器本身判错

修复预算后，`greeting-zh` 一次失败。回复是「你好！很高兴见到你。这道题是黑先做活的死活题，你先看看这块棋的眼位在哪里，想好了随时问我。」——完全符合问候规则。**判错的是 judge，不是 coach。**

没有手段区分「coach 退化」与「judge 误判」时，只能反复重跑直到变绿或删掉用例，两者都会侵蚀 eval 的可信度。为此建立了 judge 校准集（`evals/coach/judgeCalibration.ts`）：已知正确判定的回复（真实回复 + 针对失败模式编写的样例），每条附理由，每个 judge 至少各有一条 PASS 与 FAIL 样例。

校准揭示原问候 rubric **两个方向都错**：thinking 开启时误判上面那条合规回复；thinking 关闭时对真实的「宣布落子正确」泄漏 **3 次全部判为通过**。这也意味着此前「修复优先级后 5/5」的结论当时并不可靠，§3.2 的数字是换用校准后 judge 重新测得的。新 rubric 逐条列出提示词中的失败条件，10 条样例 × 3 次全部判对。judge 同样按主机默认关闭 thinking，否则 `temperature: 0` 会被忽略，校准无法区分 rubric 问题与采样噪声。

### 3.4 运维文档声称存在并不存在的账单上限

四语言 `OPERATIONS_QA.md` 将 `COACH_MONTHLY_TOKEN_BUDGET` 描述为「应用层硬性限制，防止账单意外激增」。**代码中不存在这个变量。** coach 开销实际只受用户级日/月配额、游客计数和速率限制约束，没有全局账单上限。文档已如实改写。

## 4. 测试布局统一

20 个测试文件共置于 `lib/`，91 个位于 `tests/`；其中 9 个模块两边各有一份且内容不同（`syncStorage` 一份 413 行、另一份 154 行）。加测试或评估覆盖时必须知道两处都要看，而没有任何规则说明哪边是对的。

统一到 `tests/`——这是上下文文件已写明的约定，也是改动量小得多的一边：

- 11 个独立文件移入 `tests/` 镜像路径，相对导入与 `vi.mock` 路径改为 `@/`。
- 7 对同环境、双方均无 mock 的文件合并为一个文件。其中 3 对环境不一致（node / jsdom），先验证 `tests/` 一侧在 node 下全部通过，合并后统一用 node。
- 2 对（auth、syncStorage）的 `vi.mock` 会提升到文件作用域，合并会让一方的 mock 污染另一方的用例，因此保留为两个文件并按覆盖内容命名：`auth.helpers.test.ts`、`syncStorage.backoff.test.ts`。
- `evals/coach/graders.test.ts` 移至 `tests/evals/`。

**没有丢失任何用例**：迁移前后均为 1032 个测试，测试标题多重集合完全一致，文件数 112 → 105。`tests/repo/testLayout.test.ts` 在 `tests/` 之外出现 `*.test.ts(x)` 或 `e2e/` 之外出现 `*.spec.ts` 时让 CI 失败。

未做的：两边重叠的断言（例如 `board` 两份都测 `coordEquals`）没有去重。去重需要逐条判断哪些用例冗余，删测试有丢失覆盖的风险，应单独审阅后进行。
